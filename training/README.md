# Fine-tuning the Care Assistant

> **Phase 4 (current):** retrain on context-conditioned data — see [Phase 4](#phase-4-retraining-on-context-conditioned-data) at the end. Sections 1–4 describe the first fine-tune.

This turns the Care Assistant (Phase 3 — Gemini + RAG) into one backed by a small open model you actually trained yourself, hosted for free on Hugging Face. Everything here runs outside the Next.js app, in three stages.

## 1. Generate the training dataset (runs locally, ~7 minutes)

```
npm run gen:dataset
```

This reads the 32 curated articles in `scripts/knowledge-base.ts`, asks Gemini to turn each into ~6 realistic caregiver Q&A pairs, adds a hand-written set of "boundary" examples (questions the model should decline and refer to a doctor instead), shuffles everything, and writes `training/dataset.jsonl`.

It's throttled to stay under the free Gemini tier's rate limit and caches progress in `training/.dataset-cache.json` — if it ever fails partway through (e.g. a network hiccup), just rerun the same command and it'll pick up where it left off instead of repeating already-generated articles.

You should end up with roughly 200 examples. Feel free to open `dataset.jsonl` and skim a few — each line is one training example.

## 2. Fine-tune on Colab (~15-30 minutes of your time, free T4 GPU)

1. Open `training/finetune_colab.ipynb` in [Google Colab](https://colab.research.google.com) (File → Upload notebook, or open directly from GitHub if you've pushed this repo).
2. `Runtime → Change runtime type → T4 GPU`.
3. Run the cells top to bottom. Cell 4 will ask you to upload `training/dataset.jsonl` from your computer. Cell 8 will ask for a Hugging Face access token (create one with **write** access at [huggingface.co/settings/tokens](https://huggingface.co/settings/tokens)) and your username.
4. The last cell pushes the trained model to `https://huggingface.co/<your-username>/neura-care-assistant`. Copy that repo id.

The notebook trains a LoRA adapter on top of `Llama-3.2-3B-Instruct` (via Unsloth, for speed/memory on a free GPU) and merges it into a standalone model before pushing, so it's ready to serve directly — no separate adapter-loading step needed later.

## 3. Host it on Hugging Face Spaces (~10 minutes, free)

1. Create a new Space at [huggingface.co/new-space](https://huggingface.co/new-space): SDK = **Docker**, hardware = CPU basic (free) is fine for a demo.
2. Upload the four files in `training/hf_space/` (`app.py`, `requirements.txt`, `Dockerfile`, `README.md`) to the Space repo.
3. In the Space's **Settings → Variables and secrets**, set `MODEL_ID` to the repo id from step 2 above, and optionally `SPACE_TOKEN` to a random secret string (recommended — stops random visitors from using your compute).
4. Wait for it to build (check the Logs tab for "Model loaded."). Your endpoint is `https://<your-space-name>.hf.space`.

Full details, including a test `curl` command, are in `training/hf_space/README.md`.

## 4. Point the app at it

In `.env.local` (and your Vercel project's env vars, if deployed):

```
ASSISTANT_MODEL_PROVIDER="finetuned"
HF_SPACE_URL="https://<your-space-name>.hf.space"
HF_SPACE_TOKEN="<same value as SPACE_TOKEN on the Space, if you set one>"
```

The Care Assistant route (`app/api/assistant/chat/route.ts`) will now call your fine-tuned model first, retrieval and patient-data grounding unchanged from Phase 3. If the Space is asleep or unreachable, it automatically falls back to Gemini for that request rather than failing outright — check server logs for a "Fine-tuned model unavailable, falling back to Gemini" line if that happens.

## Notes for the write-up

- Free CPU Spaces are slow (several seconds to ~30s per reply for a 3B model) and sleep after inactivity, causing a slower first request while it wakes up. This is a hosting-cost trade-off, not a training quality issue — worth mentioning if you present this.
- The dataset is synthetic (generated by Gemini from curated source articles, not scraped from real users), which is a normal and defensible approach for a small domain-specific fine-tune — just be upfront about it in your report rather than implying it's real caregiver-collected data.
- Re-running `npm run gen:dataset` after editing `scripts/knowledge-base.ts` will pick up new/changed articles for cached ones only if you delete the corresponding entries from `training/.dataset-cache.json` (or delete the whole file to regenerate everything).

## Phase 4: retraining on context-conditioned data

### Why

The first model was trained on a one-line system prompt and a bare question, but the app sends a long RAG prompt (numbered knowledge-base excerpts, the patient's care data, citation and safety rules). Benchmarked on that prompt (`evaluation/reports/2026-10-17T13-15-14`), the current model (`nashmiaadnan/neura-care-assistant`, Llama-3.2-1B) cited nothing in 5/5 answers, replied in one sentence, got the medication list wrong (p04) and invented what a neurologist said (i01). Latency on the free CPU Space was 9–13 s per answer when awake.

### Steps

1. **Generate the data** (local, resumable):
   ```
   npm run gen:context-dataset -- --dry-run                                  # check counts and a sample prompt; no generation calls
   npm run gen:context-dataset -- --teacher=gemini-flash-lite-latest --delay=6000
   ```
   Every example uses the production prompt code (`lib/assistant-context.ts`): knowledge questions with the dense top 3 articles (about 15% get only irrelevant articles, to teach "the guidance doesn't cover this"), patient-record questions over 6 synthetic patients, unanswerable questions and safety questions. A Gemini teacher writes each answer from the same prompt, and automatic filters reject answers with invalid citations or numeric dates, knowledge answers without citations, unanswerable questions that aren't declined, and safety answers without a doctor referral (`context_dataset.rejected.jsonl`, `context_dataset.stats.json`). Questions resembling any evaluation question are removed, so the benchmark stays fair.

   **Teacher choice:** the free tier allows only 20 requests a day on `gemini-3.8-flash`, so the default teacher is `gemini-flash-lite-latest`. With billing enabled (about $0.50 for the whole set), `--teacher=gemini-3.8-flash` gives a stronger teacher; delete `training/.context-dataset-cache.json` first to regenerate.

2. **Train on Colab:** open `training/finetune_context_colab.ipynb` (T4 GPU), upload `context_dataset.train.jsonl` and `context_dataset.val.jsonl`, run all cells. It trains Llama-3.2-1B-Instruct with QLoRA on the answers only (the prompt is context), keeps the epoch with the lowest validation loss, reports citation / abstention / doctor-referral rates on the validation set, and pushes to **`<you>/neura-care-assistant-v2`** — a new repo, so the current model isn't replaced yet.

3. **Serve it for the benchmark:** upload the updated `training/hf_space/app.py` to the Space (it now reports `usage`: prompt tokens, completion tokens, seconds, tokens/s) and set `MODEL_ID` to the v2 repo. Optional: `MAX_NEW_TOKENS` (default 350), `TEMPERATURE` (default 0.4).

4. **Benchmark against Gemini** on the same evaluation cases (no Gemini answer quota used):
   ```
   npm run eval:rag -- --answers --ids=k01,p01,p04,p06,i01 --provider=finetuned --delay=2 --baseline=none
   ```
   Compare with the Gemini answers in the Phase 3 report (`evaluation/reports/2026-10-17T12-56-40`) and the "before" benchmark above: citations, numeric dates, latency, and your rubric scores in the new `scoring-sheet.csv`.

5. **Only then** consider `ASSISTANT_MODEL_PROVIDER=finetuned`. Keep it **unset (Gemini)** on Vercel and in `.env.local` until the v2 model scores comparably to Gemini on the rubric — especially groundedness and safety — and answers within the app's 25 s timeout.

### Latency notes

Prompt length dominates CPU latency: production prompts are ~1,050 tokens before the answer, and the model must read all of them on every request. The Space now logs prompt/completion tokens and seconds per request, so prefill and generation cost can be read from real traffic. If v2 is good but too slow, the next steps are a paid CPU upgrade or a quantised GGUF build served with llama.cpp — measure first.
